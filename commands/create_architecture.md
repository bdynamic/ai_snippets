# Purpose

Generate an Architecture Document from the Requirements Document.
Focus on architecture, not implementation.

# Define

- Architectural overview
- Components
- Responsibilities
- Interfaces
- Data flow
- Dependencies
- Constraints
- Assumptions
- Risks

# Diagrams

Provide a high-level architectural overview that explains the system
structure and interactions. Include architecture diagrams where possible
(e.g. context diagrams, component diagrams, data flow diagrams, or
sequence diagrams). Prefer diagrams expressed in a text-based format such
as Mermaid.

# Principles to apply

- Separation of Concerns
- Single Responsibility Principle
- Modularity
- Loose Coupling
- High Cohesion
- Encapsulation
- Clear Interface Contracts
- Testability
- Maintainability
- Extensibility
- Scalability
- Reliability
- Observability
- Security by Design

# Constraints

- Every architectural element and decision must be traceable to one or
  more requirements.
- Do not add implementation details, code, algorithms, frameworks,
  libraries, protocols, or technology choices unless explicitly required
  by the requirements.
- Document missing information as assumptions or open questions. Do not
  invent requirements.
- This is a living document. Keep it aligned with the latest requirements
  and architecture.
